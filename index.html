PROBLEMS

问题与方案

每个问题一行方案——为什么这样设计，而不是那样。

🧠

上下文窗口有限，Agent 的长期记忆如何固化？

双层 MD 记忆：L1 引导层（类 CLAUDE.md，启动注入）+ L2 内容层（按需检索）；记忆固化为纯文本文件，人写人读、永不锁库。

🕸

不用向量库，怎么做关联检索？

显性知识结构：[[双向链接]] + frontmatter + 目录层级入 SQLite 图谱，与 ripgrep 全文互补——找片段用 grep、找脉络用图谱，各管一段、关联可审计。

📋

LLM 写回，如何不污染知识库？

待审闭环：Agent 生成的内容先进 pending/，行级预览 → 人工批准才落地；写回 / 补链 / 规划全部可审计，杜绝幻觉污染。

🔄

「自组织」而非「自进化」？

组织而非进化：系统只负责组织 Agent 已有的资源——记忆（链接/去重/索引/巩固）、行为（技能/上下文组装）、评估（什么用得好）；能力提升归模型与检索。

DECISIONS

方案与取舍

选了什么、没选什么，以及为什么。

  • 文件即库 vs 向量黑盒 ——正文永远是 .md，任意编辑器可打开/同步；代价是无语义召回
  • 人审 vs 全自动 ——LLM 幻觉会污染图谱，「可审计」是立身之本；代价是每次落盘多一步确认
  • 零依赖 ANSI 渲染 vs 前端框架 ——终端复制保真、无 JS 依赖；高价值内容走 /view 面板
  • bsk 外挂、Page 内化 ——不内置浏览器驱动：静态读取零依赖，动态操作用系统 Edge/Chrome headless，写操作必须人审
  • 不做 WASM / 在线市场 ——业务逻辑已在 Rust 宿主，App 深度接入 = 调宿主 API；市场只做本地导入
  • HTTP/SSE，不用 WebSocket ——iframe 经 postMessage 与父页通信，复用现有传输
MECHANISMS

已实现机制

按机制而非卖点命名——每一个都是可审计的工程事实。

机制说明
双层记忆L1 启动注入 + L2 按需检索；INDEX.md 自动生成
全文检索内嵌 ripgrep：多关键词任一命中、智能大小写、小节上下文
知识图谱SQLite 双链解析、反向链接、孤立检测、标签/项目统计
待审审核pending/ + 行级预览 + 图形审核面板（批量 / 编辑后批准）
记忆自组织/audit 规则审计 · /link 补链 · /suggest 盲区分析（全走待审）
规划引擎/task 看板 + 依赖就绪校验 + LLM 任务拆解
网页能力/fetch 静态 · /page 动态 · /page act 写侧（人审确认）
心跳同步指纹检测变化自动重建 INDEX+图谱 + 审计提示
面板渲染层/view iframe 沙箱 + postMessage 桥 + 宿主 API 鉴权
OPEN PROBLEMS

开放问题

尚未解决、正在思考的问题——探讨比结论更诚实。

  • O1检索无语义召回：换种说法可能搜不到——图谱能缓解到什么程度？
  • O2记忆只增不改：何时该巩固（压缩）与遗忘（归档）？如何不违背「人写人读」？
  • O3单 Agent 无 Subagent：长任务如何拆分与并行？
  • O4评测信号稀疏：个人场景如何验证「组织变好了」，而不是「文件变多了」？
  • O5写回审核是整篇落地：逐行合并 / 驳回编辑值得做吗？
