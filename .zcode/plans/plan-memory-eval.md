# md-agent 记忆效果评测方案（PersonaMem 式：跨会话记忆应用）

> 状态：**待评审**（2026-08-03）
> 基线：HEAD a7e7d7e（记忆断链修复已合并）
> 参考：TencentDB-Agent-Memory PersonaMem 基准（48%→76%，+59%）；md-agent CE 记账（成本侧遥测已有，**效果侧缺失**）
> 目的：为「上下文组装 v2」（注入式 → 工具化取用）提供**效果侧**对比数据——v2 前先采基线，v2 后再采一组，成本 + 效果两本账定"值不值"
> 配套：[[记忆统一模型]]（kb/notes/架构/记忆统一模型.md）——评测验证的是该模型的"记忆可被取用"环节

## 一、目标

1. 验证「记忆有没有让 Agent 在跨会话时**正确应用**用户偏好/历史决策」——即记忆是"取得到且用得上"，不只是"存得下"。
2. 为 v2（注入式 → 工具化取用）切换提供**可复现的效果基线**（CE 记账只覆盖成本侧）。
3. 样例覆盖四类记忆（偏好/决策/事实/规范），分别测"记忆应用正确率"与"编造/冲突率"。

## 二、方法：跨会话两阶段

每个样例走两个隔离会话：

- **会话 A（建立）**：通过 `/remember` 或写回块把偏好/决策/事实写入 KB（落 MEMORY 或 notes/，经待审人审——与系统写回路径一致）。
- **会话 B（验证）**：开全新会话（清 history + 重载页面，模拟新会话），提问一个**需要该记忆才能正确回答**的问题。
- **判定**：B 的回答是否**正确应用**了记忆（命中 / 未命中 / 编造冲突）。

**隔离性**：测试用独立 KB（`MD_AGENT_CONFIG` 指向临时 config + 临时 kb 目录），不污染主库；跑完清理。

## 三、样例集（5 个，覆盖四类 + 断链修复回归）

| # | 类型 | 会话 A 建立 | 会话 B 提问 | 判定点 |
|---|---|---|---|---|
| 1 | 偏好 | "回答一律用中文，禁止 emoji" | 问任意知识问题 | 回答是否中文且无 emoji |
| 2 | 决策 | "图谱重建统一走 /rescan" | "怎么重建图谱？" | 是否提及已定决策（而非泛泛或旧路径）|
| 3 | 事实 | "KB 根目录是 kb/（相对路径）" | "知识库在哪个目录？" | 是否正确引用 kb/ |
| 4 | 规范 | "写回块必须带 md-agent-save 注释" | 让 Agent 沉淀一条记忆 | 输出格式是否含标记 |
| 5 | 断链回归 | 写回一条带 `[[双链]]` 的记忆（B 修复产物）| 问该记忆涉及的主题 | 能否经双链/检索命中到相关 L2 文档 |

## 四、指标

- **正确率** = 正确应用数 / 总样例数
- **编造率** = 回答含未在 KB 的错误记忆 / 总样例数（记忆污染信号——记忆系统最危险的失败模式）
- **成本（并采）**：CE 记账 `cache_read_ratio` / `input_tokens` / `avg_tool_count`
- **判定自动化**：规则可判的（emoji / 关键路径 / 标记）自动核对；语义判断人工抽查

## 五、执行步骤

1. 建隔离测试 KB + 5 个样例的会话 A 写入（可脚本化：POST /api/file + /api/kb/pending/approve）。
2. 会话 B 用真实 LLM 提问（走完整 ask() 链路，不 mock），记录回答原文。
3. 每样例跑 2-3 轮（LLM 有随机性），统计正确率/编造率。
4. v2 切换后重复 1-3，对比两本账（成本 + 效果）。
5. 结果沉淀回 kb（评测结论进 MEMORY 或架构笔记，遵循"知识人写人读"）。

## 六、与 v2 的衔接

- **v2 前**：本评测出效果基线（配合 CE 记账的成本基线）。
- **v2 后**：同法重测，成本 + 效果对比。
- **判定阈值**：v2 正确率不下降（≥基线）且成本改善显著 → 采纳；否则回滚（还原点 tag `restore-point-ui-opt` 仍在）。

## 七、前置/依赖

- 样例 5 依赖 B（记忆断链修复，已合并 a7e7d7e）。
- 需要真实 LLM 配置（DeepSeek，隔离 KB 的 config 指向临时目录）。
- 不依赖 v2——基线可在现状（注入式）下直接采。

## 八、基线结果（v2 前，2026-08-04 采）

**效果侧（隔离 KB + 真实 LLM，会话 B 逐样例全新会话）**：

| # | 类型 | 会话 B 判定 | 结果 |
|---|---|---|---|
| 1 | 偏好（中文禁 emoji）| 回答中文、无 emoji | ✅ |
| 2 | 决策（图谱重建走 /rescan）| 明确「用 /rescan，不要用 /sync」| ✅ |
| 3 | 事实（KB 根 kb/）| 「知识库根目录是 kb/（相对路径）」+ 引用 MEMORY | ✅ |
| 4 | 规范（写回带 md-agent-save）| 产生写回块 → 待审记忆条目 | ✅ |
| 5 | 双链（托盘应用）| 准确描述 + 引用 [notes/架构/托盘应用.md:6] | ✅ |

- **正确率 5/5（100%）· 编造率 0**（全部有来源引用或写回落盘验证）
- 样例 1-3 的记忆应用走的是 **memory_summary 摘要注入**（L1 常驻）——即 v2 要改为「工具取用」的那条路径；v2 后正确率保持 + 成本下降 = 净收益

**成本侧（CE 记账，7 次 question 含 2 次重试）**：avg input 1745 tokens/问 · cache_read_ratio 72.3% · avg_tool_count 0 · overflow 0

**附带发现**：
- L0 会话快照端到端验证通过：问答对落盘 `kb/sessions/`，不入图谱（0 节点）、不可检索（命中均来自正式文档）
- 缺口：写回记忆为**裸文本**（无 `- ` bullet）时进不了 `memory_summary`（只收 bullet 行）——真实写回路径存在潜在丢记忆，待立项修复（写回格式对齐 bullet）

**v2 对比目标**：正确率 ≥ 100%（不下降）且 input_tokens 显著下降 → 采纳；否则回滚（`restore-point-ui-opt`）。

## ✅ 评测结果沉淀（2026-08-04）

### v2（工具化 B 半：注入前缀保留 + 工具能力）——他窗口评测，5 样例
- 正确率 5/5（=基线），编造率 0
- avg 1812 tokens/问 vs 基线 1745（+3.8%）——成本未改善
- 结论：**v2 采纳**（工具取用链路实测工作：Q5 完整走 search→file→引用；消除中文启发式提取的脆弱性）；但 token 未省因前缀（L1 规范全文+摘要）仍是 input 大头 → **C 半步是真正落点**

### C 半步（前缀瘦身：L1 全文移出前缀，read_l1/search 按需取）——本会话评测，5 样例同口径 A/B
| 指标 | 基线（注入式） | C 半步（瘦身+工具） |
|---|---|---|
| 正确率 | 5/5 | 5/5 |
| avg input | 5165 | 2731（**-47%**） |
| avg total | 6016 | 3195（**-47%**） |
| cache 率 | 63.9% | 74.1%（+10pt） |
| 工具行为 | 注入前缀+工具双冗余（read_l1/search/graph 仍被调） | 全部主动调工具取用 |

- 样例：决策·检索引擎（search）/ 规范·沉淀位置（memory_search）/ 事实·托盘架构（memory_search+file）/ 双链·记忆统一模型（graph.linked+backlinks）/ 写回·沉淀表达（read_l1）；全新会话、无 history、真实 DeepSeek
- 结论：**采纳**——正确率不降 + 成本显著改善（input/total -47%）；cache 率反升（瘦身前缀更稳定）
- 关键洞察：基线在回答规则「必须先调工具取用」下也会调工具 → 注入前缀 + 工具 = 双冗余；C 半步移除前缀冗余即收益来源
- 实现：`core.js` buildGuidePrefix 引导语条件化（hasL1，无 L1 段时不输出悬空引导）；`app.js` ask() 两处 buildGuidePrefix 在 llmConfigured 时 guideText/memoryText 传空（正常路径 + fresh-window 降级）
- 回滚：还原点 `restore-point-interaction-converge`（此前 UI 还原点）之上，本改动在 `restore-point-interaction-converge` 后，若需回滚 git revert 对应 commit 即可
